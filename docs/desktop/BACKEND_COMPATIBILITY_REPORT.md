# Backend compatibility report — 2026-11-03

Production API 0.76.1 is reachable from the existing macOS Electron build. This is public contract/handshake evidence, not authenticated production acceptance.

| Investigation | Actual evidence | Result / remediation |
|---|---|---|
| Production API 403 | Python urllib requests received Cloudflare 403, including public config/server-info/social config. The same configured origin returned 200 in Node discovery and actual Electron; no host, WAF, authentication or CSP override was used. Both direct public API ingress and loopback health are healthy. | Classified: Cloudflare error 1010, `browser_signature_banned`, `owner_action_required=true`, on the default urllib client. This is edge browser-signature filtering, not the backend's account authorization response. Node and actual macOS/Windows Electron public requests pass without spoofing or changing targets. Correlate the recorded ray/time with owner edge logs if non-browser access is required; do not disable protection globally or bypass it. See production-edge-1010.json and [Cloudflare's explanation](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/). |
| Promotions preference 404 | The isolated backend at local media-release commit `b34d3ee82eeb82cdcce8d2e5af0ad06ead17398d` returns 404. Current production returns 401 to unauthenticated GET, including through actual Electron and direct loopback. | Production has the protected route; the old local test source lacks the client's newer preference contract. Obtain deployed source/contract artifact and test authenticated GET/PUT with authorized QA accounts. Do not invent an alternative endpoint or treat 401 as authenticated verification. |
| Provider configuration | Production `/v2/auth/social/config` advertises Google/Discord and `authorizeOrigin=https://web.meldiq.app`. Runtime social web/public origin matches. | UI config works; Apple is not advertised and must not be claimed enabled. Actual provider sign-in, account linking, replay/unsolicited return rejection and cancellation require dedicated provider accounts. The compatibility adapter currently asks for the existing `android` native return flow; a separately registered desktop provider platform is not claimed. |
| Desktop client identity | Renderer reuses existing `ApiClient` with account bearer tokens, `credentials=omit`, existing device enrollment and API version contracts. Desktop native auth adapter reuses existing proof-bound native return flow. | No invented client API/header or hardcoded credential was added. An authenticated Windows run must verify backend acceptance/device naming and session/key restoration. |
| Callback compatibility | Existing source supports native `android` flow and proof-bound receipt redemption used by desktop. Pending callbacks and invite capture have tests/smoke evidence. | Owner must confirm deployed registrations and `meldiq://auth/callback` return on installed Windows. Provider browser completion and Store callbacks are not verified by static source or unit tests. |
| S3 upload/download origins | Existing bucket and exact S3 hostname confirmed from deployed public fields/nginx; backend supports direct-upload and attachment-proxy features. The restricted API profile cannot inspect CORS; the existing operator profile confirmed GET/HEAD/PUT for the web/admin origins and one-day incomplete multipart cleanup without changing configuration. | Resolved the empty desktop connection list with three exact S3/LiveKit origins already allowed by the actual deployed website CSP; see production-origin-policy.json. Actual signed transfer evidence, additional transport requirements and application cleanup verification remain required. Do not add wildcards or bypass authorization. |
| API/WS origin rules | No `WEB_ORIGINS` runtime value; OPTIONS has no CORS allowance. Actual same-origin Electron API and unauthenticated WSS handshake work. | Keep packaged same-origin architecture. Authenticated socket frames, reconnect and any cross-origin API use need evidence. Empty browser CORS is not automatically a defect in a same-origin deployment. |
| Calling | LiveKit configured; existing rtc host answers HTTPS. | Actual room grants, expiry, E2EE, media, hotplug, screen sharing, reconnection and sleep/wake unverified. |
| Payments | Live PayPal and one available live public plan observed; Stripe secret absent in inspected runtime. | Read-only catalog works. Transactions require an isolated sandbox deployment. No live checkout, subscription, gift or payment operation was executed. Server pricing/entitlements remain authoritative. |
| Database/notifications | Atlas and Redis healthy; backend has FCM and SMTP configuration. | No desktop database connection or permanent cloud credentials. Actual cross-device data, native notification delivery and key recovery still require QA accounts. |

Read-only infrastructure inspection did not deploy or change backend configuration, databases, credentials, allowlists, DNS, AWS or providers. Existing deployment docs can be historical: the inspected 0.76.1 runtime supersedes older 0.69/0.72/0.74 reports. Do not use an old runtime/CLI to mutate current production data.
