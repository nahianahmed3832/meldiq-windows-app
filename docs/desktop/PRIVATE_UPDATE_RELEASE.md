# Release-key authenticated Windows updates

The owner explicitly selected private release keys on 2026-11-03: generate the key, make the Windows app publishable and directly updateable, then publish the website download. This authorizes the new update trust model and website feed. It does not certify untested production features or supply an Authenticode identity.

The Ed25519 private key is stored outside the repository at `~/Library/Application Support/Meldiq/release-signing/update-private-key.enc`, encrypted with macOS Keychain and owner-only permissions. Only the public key in `config/update-key.json` is compiled into clients. No private signing key is uploaded to GitHub, the website, the renderer or the packaged app. Back up the signer directory together with an encrypted backup of the owner's macOS Keychain; the encrypted file alone is not portable. Never replace a lost key and pretend existing clients trust the new one.

The existing electron-updater/NSIS download and install engine remains. A custom provider authenticates a domain-separated signed JSON payload before offering or downloading an update. It binds application, Windows x64, channel, version, sequence, expiry, exact HTTPS artifact origin/name, byte length, SHA-256 and SHA-512. Local per-channel checkpoints reject stale or conflicting metadata across restarts. Downloaded bytes and the signed envelope are checked again before installation. There is no unsigned-manifest fallback.

New installations default to automatic checks/downloads. A downloaded update installs silently on a safe application exit, then relaunches. Existing explicit user preferences remain respected. Calls, transfers, screen capture and payment windows prevent installation/restart. Windows publisher Authenticode verification remains available for the separate certificate-backed distribution. The private-key distribution uses release-key authentication instead; its installer remains unsigned to Windows.

The website feed is `https://meldiq.app/desktop-updates/windows/<channel>/release.json`. Assets use immutable version/hash paths on the same website. Upload and verify assets before atomically promoting signed metadata. The private key remains on the owner's Mac; CI builds unsigned binaries containing the public key and records their exact hashes. The owner-authorized local signer signs only reviewed candidate metadata.

Before website publication, native Windows qualification must pass: reject a modified signature; reject a corrupted installer; automatically check/download and upgrade between two installed NSIS versions; refuse installation while busy; retain local fixture account/message data and OS-sealed session through the actual upgrade. The isolated qualification app has its own app ID, profile and channel. Its control hooks are removed from public binaries by the build, with an explicit package assertion. Fixture retention is not an authenticated production-backend test.

Production account/media/call/payment acceptance and physical hardware benchmarks remain separately documented in the existing reports. Private update-key signing must not be described as a Windows-verified publisher certificate or full feature acceptance.

## Operator procedure

Use the owner's Mac for signing. Generate/reuse the protected signer with `npx electron scripts/update-key.cjs generate`; only its public identity may be copied into `config/update-key.json`. The active key fingerprint is `abb61b4909c9803f0e1f360b441ef8e65c35c98271fe9957b82d76d48af41f8d`. Do not delete the encrypted key or the matching Keychain entry. Key rotation requires a release trusted by the existing key that also embeds the replacement public key.

1. Bump the application version, commit and push the reviewed source. Dispatch `desktop-private-prepare.yml`. Its Windows job runs the regression checks and produces one public candidate and two isolated updater-lab candidates in a draft GitHub release. CI receives no signing key.
2. Run `node scripts/stage-private-candidates.mjs --run <successful-preparation-run>`. The operator script checks provenance, stages exact hashed assets on the existing website host, signs metadata locally and publishes only the three isolated qualification feeds. The public candidate and stable metadata remain unpublished.
3. Dispatch `desktop-private-qualify.yml` with `candidate_run=<preparation-run>`. It installs the real lab EXEs on Windows, rejects a bad signature and corrupt artifact for the correct cryptographic reasons, upgrades automatically with retention checks, then installs/launches/inspects/uninstalls the actual public candidate.
4. After that complete job passes, run `node scripts/publish-private-release.mjs --qualification-run <successful-qualification-run>`. It verifies the recorded native evidence, source identity and every authenticated artifact field; publishes immutable binary/checksum/release details; then atomically promotes the signed stable envelope under the production release lock. It refuses rollback/downgrade. No unsigned YAML feed is published.
5. Set the landing site's exact version, bytes, hash and immutable paths in `src/lib/windowsDownload.ts`; run its type/lint/unit/build/browser checks. Deploy using its existing guarded atomic workflow and verify the live page, signed feed and binary integrity. The website source is preserved in this repository at `packages/meldiq_landing_website`.

Signed metadata expires after 90 days. Issue and verify fresh metadata before expiry, even if no new installer is needed; rerunning the same staged/qualified candidate procedure produces a new sequence and expiry. An expired feed fails closed and does not disable the installed messaging client. Never extend timestamps by editing the hosted JSON without signing it.

Version 0.1.0 has no enabled/pinned updater. Its users must install 0.2.0 manually once. Subsequent compatible releases use the new signed feed. Default checks run 15 seconds after launch and every six hours; automatic mode downloads and installs on safe exit. Users can select manual behavior in Desktop settings.
