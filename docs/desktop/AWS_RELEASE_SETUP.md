# AWS release setup — prepared, not deployed

No AWS resources, production DNS, account database, upload bucket or media policy was changed. The following requires an approved release account/region, domain control, certificate, release role and deployment authorization.

Use a separate private S3 general-purpose release bucket with public access blocked, bucket-owner-enforced object ownership, encryption at rest, versioning and no website endpoint. CloudFront OAC must always sign requests to that regional REST origin. The read policy grants the CloudFront service principal GetObject only on release objects and restricts `AWS:SourceArn` to the one distribution ARN; also deny insecure transport. Generate and validate the concrete policy after the actual account/bucket/distribution are known. No broad release permissions go to the app. See [AWS OAC setup](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

Create an ACM certificate in the CloudFront certificate region for updates.meldiq.app, validate ownership, add the alternate domain to the distribution, then approve DNS alias/CNAME to its assigned hostname. Enforce viewer HTTPS, permit only GET/HEAD, and apply an appropriate security response headers policy. Do not attach authenticated client API headers or cookies to this public binary distribution. No remote HTML is served into the privileged renderer.

Object layout is `windows/stable/`, `windows/beta/`, `windows/canary/`, with future `macos/` and `linux/`. EXEs use `Meldiq-Setup-<version>-x64.exe`; blockmaps and updater-generated metadata keep their generated names. A signed binary is immutable and never overwritten at its versioned key. Development artifacts cannot be promoted.

Use a cache behavior before the default for `windows/*/*.yml`: minimum TTL 0, short/revalidation caching, metadata `Cache-Control: no-cache, max-age=0, must-revalidate`. Versioned binaries/blockmaps use long immutable caching. Invalidate only metadata after promotion and verify Age, Cache-Control, ETag, hashes and downloadability from more than one location. CloudFront minimum TTL can override origin no-cache, so it must be zero for metadata. See [AWS cache behavior documentation](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesCacheBehavior.html).

Use GitHub OIDC with a protected desktop-release environment and least-privilege short-lived role. Scope object writes to the release prefixes, reads to verification, ListBucket by prefix and CloudFront invalidation to the one distribution. The trust policy must bind the audience and this repository/environment's actual subject. This newly created repository may use immutable owner/repository IDs in its OIDC subject; inspect the issued subject before creating the policy. Do not assume the historical repo:name subject format. See [GitHub OIDC for AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws).

Enable encrypted restricted CloudFront/S3 access logs, CloudTrail write data events and CloudWatch metrics/alerts for distribution errors, write changes and unusual volume. Choose WAF rate limits that permit normal range downloads/updates; evaluate paid Shield Advanced only against the required risk and budget. Logs may include request metadata; restrict retention/access. Costs include artifact/version storage, requests, CDN transfer, logs/CloudTrail, invalidations and optional security services; no costs or account-level capacity were assumed. Check [S3 pricing](https://aws.amazon.com/s3/pricing/) and [CloudFront pricing](https://aws.amazon.com/cloudfront/pricing/) for the selected region and traffic.

Promotion procedure: retrieve the approved signed CI artifact by immutable run/commit; verify EXE signature and checksums; upload binaries and blockmaps with immutable headers; fetch and compare through CDN; upload metadata last with revalidation headers; invalidate metadata; fetch metadata and every referenced artifact; test a staged client update and preservation of session data. Store notes, provenance and measurements. The current workflow creates candidates only and performs no cloud writes.

Recovery: halt promotion and staged rollout; retain old artifacts; publish a higher corrective version. S3 versioning permits recovering accidentally corrupted metadata with explicit review, but never silently downgrade installed clients. No database migration is part of desktop release infrastructure.
